# 播放中尽快混入（2026-10-20）

云端 `/listen/smart/` 新增“尽快混入”：选定下一首后，点击一次，从实际播放位置附近找点、准备并自动安排交接。过期的判断结果也能点“重新找点并混入”，继续向后找，不必倒回去试听。原来的单独准备、手动选择方案和试听仍保留。

原页面只准备固定接点，再等第二次点击确认。手机同版自动续播还会优先选择歌曲后段。这两种流程都不能代替用户中途发起的附近接点请求。

## 选点与等待

新请求仍调用 `planContinuous`，保留来源绑定、人声评分、完整局部拍点、65 ms 最大偏差、动态 EQ 和 0.95–1.05 变速范围。先搜索短等待范围，再扩大；不使用自动续播的后段保留限制。窗口进入和退出都沿用原有素材及完整小节，未通过检查就保持当前播放。

冷准备提前量内（当前 40 秒）已有准备结果时，校验歌曲和接点后直接加载并调度。尚未准备时，先留出 40 秒，再依次以 18、30、60 秒的搜索预算择优。预算约束退出点，因此这是附近可执行范围内的质量排序，不是逐毫秒最短等待算法。

40 秒是根据这次云端首次任务约 30 多秒设置的准备余量，不是速度承诺。它与旧本机预生成素材的即时调度不同。接点失效会停止本地等待，增加准备余量并继续找后续点；一次最多三个候选。云端没有取消任务接口，已提交的任务可能继续运行。

渲染片段与 B 正文均下载、校验和解码后，才交给同一个 AudioContext。停止、暂停或取消会阻止旧请求调度。transport 的 `arm` 新增可选取消信号，覆盖最后一次缓存加载至调度前的窗口；已有调用保持兼容。

- 新回归先复现“一次请求只准备、不调度”，以及 arm 最后加载阶段取消后仍可能排入交接的问题；修复后通过。
- TypeScript 全套 835 项通过，12 项外部资料测试按配置跳过；类型检查和独立复核通过。
- 本机网页从 Attention 约 54 秒发起冷准备，最终在 101.028 秒开始混入 HIPHOP；交接和正文接管两个音频线程观察均 `late=0`、输出非零。
- 正式网页从 Attention 23.881 秒发起请求，复用已准备的 37.021 秒接点，43 ms 内完成调度；46.173 秒交接结束，HIPHOP 从对应正文继续。请求之后没有 `track_start`，两个音频线程观察均 `late=0`、输出非零。这是调度证据，不代表设备延迟或主观听感。
- 最终 r2 构建再次完成同曲对，复用准备结果后自动交接，两个音频线程观察仍为 late=0、输出非零。
