# 模块清理决定：保留已核对的后续实现，去掉重复旧版

2026-09-13，用户已明确不要求兼容旧手机 API，并要求 modules 保留最新实现、去掉旧版。

**进一步确认：保留的 11 个非预处理模块属于第一版实现（含后续维护版本），第二版不一定需要。是否采用、复用还是重写，须由对应负责人逐项确认，当前全部待确认。** 未确认前，不作为第二版必做功能、默认依赖或部署要求。保留代码仅供评估，不改变现有正式预处理的采用决定。

## 本轮实际做了什么

1. 核对远端模块 v0.2、部署 v0.3、clean-core 后续实现；不是仅依据目录中的旧 v0.1 说明判断版本。
2. 11 个非预处理模块同步到选定远端提交 `15b8663` 的实现，仅更新对应模块，不合并整分支。
3. 删除 `modules/audio-preprocess`、`modules/stem-separation` 的旧代码、测试和打包合同，目录只留指向正式实现的 README。
4. 保留当前正式分析代码：`preprocessing/` 与 `music_analysis/drum_analysis/`。不导入远端较旧的 base_analysis 覆盖 SongFormer。
5. 正式测试仍引用的 `pre-style-features-v5.schema.json` 迁到 `contracts/schemas/analysis/`，逐字保留。这是已有内部特征格式，不因此升级成新的公开交付合同。
6. 删除顶层旧 BASELINE-v0.1.0 清单，改为 CURRENT.json；重写模块版本清单和测试入口，不另留两套源码。

## 为什么不是将旧分析拼到新分析里

旧 audio-preprocess 主要围绕 dj_structure_v2 切点候选；旧分轨分析的质量缺失处理和特征证据与当前实现不同。将这些代码直接合入当前引擎会改变结果含义。现在只保留已经用于曲库交付的正式流程。

library-catalog 虽已同步较新实现，其 original/四轨 DTO 仍不等于 NAS 完整 manifest，不能据此宣布新 APK 后端或完整资源下载已完成。

## 怎样看保留版本

以 [当前模块清单](../../modules/REGISTRY.md) 为准；来源 commit、文件指纹及模块合同/安装包两种版本分别记录在 [CURRENT.json](../../modules/CURRENT.json)。上轮文档的“全部保留旧源码”已被本轮决定取代。

其他模块同步只代表仓库采用较新源码，不表示真实设备完成新链路联调。逐函数差异不通过随意改号掩盖；本轮用来源校验和独立测试验证引入的代码。

## 新 APK 与旧后台

新手机接口按新 APK 源码/页面和当前预处理发布合同重构；新 APK 源码待用户上传，当前不推测页面或新增接口。

app 内旧 Python 分析导入转发只是过渡期服务保护，不是旧手机 API 兼容要求。本轮未停用现有线上 API、未删数据库表。待新后端替代调用实现并验收后，再移除旧业务路径。

## 恢复与未改动范围

本次移除的旧文件仍在 Git 提交 `3482daf` 及历史标签中，可按文件恢复。没有删除远端分支、不可变标签、模型、音频、标注或 NAS 数据；没有切换默认分支或部署设备。
