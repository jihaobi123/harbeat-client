## 3. 重叠文件如何修改

### `app/modules/library/`

这是当前风险最高的重叠区：后端负责业务路由/表/Worker，算法负责分析函数和语义。

规则：

1. 后端不得在算法函数内部加入 SQLAlchemy 业务提交；
2. 算法不得在 router/model 中加入临时算法字段作为正式合同；
3. 拆分 adapter 前，对 `background_tasks.py` 的修改必须双方评审；
4. 新算法输出先进入 `contracts/schemas/analysis`，再由后端映射到 artifact/DTO；
5. 旧 `LibrarySong` 字段兼容由后端 adapter 负责，算法不长期维护两套业务持久化。

### Manifest/runtime metadata

后端负责资源身份、授权、生成和发布；RK负责可执行性、缓存和兼容；算法负责音乐时间网格/过渡语义；手机只评审展示和触发流程。

任何一方都不能单独宣布 Manifest ready。

## 5. 首轮合同冻结会议必须得到的结论

### 算法与后端

- Core/Stem/Feature/Style 的输入输出 Schema；
- Stage success/partial/failed 门；
- timeout/cancel/retry/error；
- pipeline/model/calibration version 与幂等键；
- staged file → media asset 的交接方式。

### 后端与手机

- OpenAPI 的 ID、分页、权限、状态和错误；
- Preview 与完整播放边界；
- Upload/Analysis/Publication 分离；
- 中央设备在线与 RK 局域网连接的区别。

### 后端、RK 与手机

- 配对流程、短期 RK session 和撤销；
- Capability、State、Operation、Event；
- Manifest/Sync 状态和恢复；
- 手机只访问 edge-agent 的端口与路径。

### 算法、RK 与后端

- runtime metadata 的最小字段、毫秒单位和大小上限；
- 低置信网格时 RK 禁用哪些强量化；
- Stem/Render codec/采样率/声道；
- audio-engine 与 metadata/plan 的版本兼容。

## 6. 可以并行开发的内容

- 后端可以先建立 Alembic、Identity、Track/UserLibrary、AnalysisRun/StageRun 和 fixture Worker；
- 算法可以先修 Schema 漂移、Style fail-closed、stage adapter 和 fixtures；
- 手机可以先完成 OpenAPI 生成链、双连接状态、页面 ViewState 和共享 Mock；
- RK 可以先完成 SQLite、Capability、Operation/Event、edge-agent 单入口和 simulator。

## 7. 合同冻结前禁止完成式开发的内容

- 后端不能根据旧算法扁平字典永久设计 AnalysisArtifact；
- 手机不能根据旧手写 JSON 完成中央/RK客户端；
- RK 不能根据当前 App 路径固定 `/live/intent` 或 8 Pad；
- 算法不能根据未冻结 Manifest 自行生成 asset UUID 或公网 URL；
- 四方不能各写一套 status/error enum 再等联调时转换。

## 8. 集成顺序

```text
合同 fixtures
→ 后端 Mock / 算法 fixture Worker / RK simulator
→ 各端合同测试
→ Jetson 后端 + 算法 adapter
→ App + RK simulator
→ App + RK真机
→ Jetson/NAS + 阿里云 + App + RK全链路
```

每一级通过后保留测试报告和版本，不能跳过中间层直接在真机上“边试边定协议”。
