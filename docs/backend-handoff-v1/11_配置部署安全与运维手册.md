## 1. 2026-08-28 现状基线

通过当前私网访问核对到的实际拓扑：

### 阿里云

- Nginx 正监听公网 80/443，承担入口；
- 存在轻量 `HarBeat Gateway 0.1.0`，提供 `/health`、`/jetson/health`、`/edge/registry` 等控制面和反向代理路径；
- 未发现 HarBeat 业务 PostgreSQL 5432、Redis 6379 或业务 FastAPI 8000 对公网/Tailscale暴露；
- 没有音乐分析 Worker/业务数据库运行在阿里云。

结论：阿里云当前身份确实是公网 Gateway/私网隧道，不是业务主机。

### Jetson + NAS

- Jetson 上运行完整 HarBeat FastAPI `:8000`，当前路由约 93 条；
- PostgreSQL 14 仅本机 `127.0.0.1:5432`，数据库名 `rhythm_prism`；
- Redis 仅本机 `127.0.0.1:6379`；
- NAS CIFS 挂载在 `/mnt/nas/harbeat`，音乐目录位于其下；
- 当前 Uvicorn 是单 Worker；没有独立 RQ/Celery 分析 Worker；
- `ENABLE_STARTUP_ANALYSIS=0`，应继续保持；
- 当前发布位于 `/opt/harbeat/current` 体系，运行版本与工作分支/模块合同存在漂移；
- 当前 `PUBLIC_ASSET_BASE_URL` 指向私网/Tailscale 风格地址的风险配置。普通 RK 不加入 Tailscale，必须改成阿里云公网 HTTPS 域名。

## 2. 目标生产拓扑

```text
Internet
  |
  v
Aliyun public :443
  nginx/gateway: TLS, rate limit, upload/range, access log
  |
  | private tunnel (Tailscale/FRP; only allow Aliyun -> Jetson API/assets)
  v
Jetson loopback/private interface
  harbeat-api              PostgreSQL 14+
  harbeat-dispatcher       Redis 7+
  harbeat-worker-core      NAS mount
  harbeat-worker-stem      local temp/model cache
  harbeat-worker-feature
  harbeat-worker-media
  harbeat-reaper
```

端口原则：

| 节点/端口 | 绑定 | 对外规则 |
|---|---|---|
| 阿里云 443 | 公网 | 唯一生产业务入口 |
| 阿里云 80 | 公网 | 仅 301 到 HTTPS/ACME |
| Jetson API 8000 | loopback 或隧道专用 IP | 仅 Gateway/本机；不得公网 |
| PostgreSQL 5432 | `127.0.0.1`/容器私网 | 不经 Gateway/公网 |
| Redis 6379 | `127.0.0.1`/容器私网 | 不经 Gateway/公网 |
| RK edge 9000/9001 | 手机热点局域网 | 手机短期授权访问 |
| RK sync 9100 | `127.0.0.1` | 只供 edge-agent |
| audio Unix socket | 本机 | 只供 edge/input 服务用户 |

## 3. 发布物与目录

推荐 Jetson 不可变发布：

```text
/opt/harbeat/
  releases/<release_id>/       # 只读代码/venv/静态资源
  current -> releases/<id>/    # 原子 symlink
  shared/
    env/production.env         # root:harbeat 0640
    models/                    # 模型与 manifest/hash
    logs/                      # 如不完全用 journald
    tmp/analysis/              # 本地 SSD 临时空间
    runtime/                   # socket/pid（或 /run/harbeat）
/mnt/nas/harbeat/
  assets/                      # 目标不可变对象
  staging/                     # 上传/结果暂存
  backups/                     # 如策略允许；数据库备份最好另有异机副本
```

每个 release 必须包含：`git_sha, release_id, built_at, dependency lock hash, analysis pipeline/model manifest, OpenAPI version, Alembic revision`。禁止在 `/opt/harbeat/current` 中现场手改源码。

## 5. 本地开发标准流程

### 5.1 要求

- Python 3.10+（生产固定具体 minor，建议与 Jetson 一致）；
- PostgreSQL 14+；Redis 7+；ffmpeg/ffprobe；
- 算法开发按模型要求安装 libKeyFinder、Essentia、Demucs、Beat/Downbeat 依赖；
- NAS 在开发环境使用独立测试目录/volume，不指向生产挂载；
- Node 18+ 用于 Web，Flutter SDK 版本由 `mobile/` 锁定。

### 5.2 目标命令（后端需实现/维护）

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env

# 在更新后的开发 compose 中仅启动依赖
docker compose up -d postgres redis

alembic upgrade head
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

# 独立终端
python -m app.workers.run --queues analysis.core,media.derivatives
python -m app.workers.dispatcher
python -m app.workers.reaper

pytest -q
```

当前仓库尚未具备完整 Alembic/Worker 入口，上述是 P0 交付目标。改造完成前的 `Base.metadata.create_all()` 只允许临时测试，生产必须 `ENABLE_DB_CREATE_ALL=0`。

### 5.3 开发数据隔离

- `.env` 永不提交；提交 `.env.example` 只能含 `<placeholder>`；
- dev/test 数据库与生产完全分离；测试自动创建独立 schema/database；
- 测试媒体使用短小、许可明确的 fixtures，不复制用户生产音频；
- 外部 metadata 默认关闭，合同测试使用 stub；
- 本地 App 指向 `http://127.0.0.1:8000`；真机通过受控局域网 dev gateway，不把生产 secret 下发开发机。

## 6. 配置分组

所有配置由 Pydantic Settings/等价层统一加载、类型校验并在启动时输出“键名 + 是否设置”，绝不输出 secret 值。未知生产配置建议 fail fast。

### 6.1 API/数据库/认证

| 变量 | 必需 | 生产要求 |
|---|---:|---|
| `APP_NAME` | 是 | `HarBeat` |
| `APP_ENV` | 是 | `production`；控制 docs/debug/CORS |
| `APP_HOST/APP_PORT` | 是 | Jetson 内部绑定；8000 |
| `DATABASE_URL` | 是 | PostgreSQL URL；通过 secret 文件；最小权限用户 |
| `REDIS_URL` | 是 | loopback/私网；认证/ACL 如跨容器 |
| `JWT_SECRET` | 是 | ≥32 随机字节；不使用样例值 |
| `JWT_ALGORITHM` | 是 | P0 可 HS256；多服务扩展建议 EdDSA/RS256 并轮换 key ID |
| `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` | 是 | 建议 15–30，不沿用当前 10080 分钟样例 |
| `JWT_REFRESH_TOKEN_EXPIRE_DAYS` | 是 | 建议 30；rotation/revocation |
| `PASSWORD_ARGON2_*` | 是 | 由安全基准定 cost，启动自检 |
| `CORS_ALLOWED_ORIGINS` | 是 | 明确 allowlist；生产禁 `*` + credentials |
| `ENABLE_DB_CREATE_ALL` | 是 | 生产 `0` |

`deploy/.env.example` 当前含看似真实且弱的 JWT 样例和超长 access TTL，必须替换为明显 placeholder/安全默认值。

### 6.2 存储和公网资产

- Key：`KEYFINDER_CLI`, `KEYFINDER_TIMEOUT_SECONDS`, `KEY_MADMOM_COMMAND`, `KEY_MADMOM_TIMEOUT_SECONDS`, `CHROMA_PATH`；

### 6.5 外部元数据

`SPOTIPY_CLIENT_ID/SECRET/REDIRECT_URI`, `DISCOGS_USER_TOKEN`, `LASTFM_API_KEY` 等只能从 secret store/env 加载，默认关闭 `ENABLE_EXTERNAL_MUSIC_TAGS=0`。外部服务失败不应使核心分析失败；遵守许可证、速率和缓存期限。

## 7. Systemd 服务要求

示例（不是可直接复制的 secret 配置）：

```ini
[Unit]
After=network-online.target postgresql.service redis.service mnt-nas-harbeat.mount
Requires=mnt-nas-harbeat.mount

[Service]
User=harbeat
Group=harbeat
WorkingDirectory=/opt/harbeat/current
EnvironmentFile=/opt/harbeat/shared/env/production.env
ExecStart=/opt/harbeat/current/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=/mnt/nas/harbeat /opt/harbeat/shared/tmp /run/harbeat

[Install]
WantedBy=multi-user.target
```

每个 Worker/dispatcher/reaper 独立 unit，使用资源限制。Stem Worker 可绑定 GPU；API 不应有写全部系统路径权限。

RK 已有 `cypher-audio-engine/edge-agent/input-daemon/sync-worker` units 和 target，需修正：服务/日志 unit 名一致、9100 loopback、依赖 audio socket ready、EnvironmentFile 权限、SQLite/缓存写路径、WatchdogSec 和重启恢复测试。

## 8. 阿里云 Nginx/Gateway 要求

- TLS 1.2+、自动续证和到期告警；HTTP 仅重定向；
- `/api/v1/uploads/*` 单独 client_max_body_size、长上传 timeout；
- `/assets/*` 支持 Range/206/Content-Length/ETag，不启用会破坏签名的改写；
- 普通 API 短 timeout；分析只返回 202，不持有 30 分钟请求；
- 按 IP + user/device subject 限流；登录/配对/asset grant 单独更严；
- 只转发必要 header，生成/保留 X-Request-Id、X-Forwarded-Proto；
- 隐藏 Server/debug；access log 对 Authorization、cookie、签名 query 脱敏；
- Jetson 隧道不可用返回 503 + Retry-After，不落本地第二数据库；
- Gateway 健康区分自身 live 与 Jetson upstream ready。

## 9. 健康检查

| 接口 | 语义 | 检查内容 |
|---|---|---|
| `/health/live` | 进程活着 | 不访问重依赖，<100ms |
| `/health/ready` | 可接业务 | DB、Redis、NAS read/write probe、migration 版本；不执行模型 |
| `/health/analysis` | Worker 能力摘要 | 最近心跳、队列最老年龄、模型 manifest、GPU/磁盘 |
| `/api/v1/system/build` | 版本 | release/git/db/contract/model set |
| Gateway `/health` | 网关活 | Nginx/control-plane |
| Gateway `/jetson/health` | 上游活 | 隧道和 Jetson ready 摘要 |

NAS write probe 写受控小临时对象并清理；不能在每次 readiness 对整库/模型做重扫描。

## 10. 安全基线

### 10.1 身份

- 密码使用 Argon2id；登录成功时可透明升级 cost；
- Access token 15–30 分钟，refresh rotation、hash 存储、family replay detection；
- 所有用户对象从 token `sub` 获取，不接受请求 body 的 user_id 代替鉴权；
- Device token 与用户 token audience 分离；device token hash 存 DB；
- Pairing code TTL/尝试限制/物理确认；临时控制授权必须过期；
- 管理接口需要 reviewer/admin，关键封禁/物理删除建议二次确认。

### 10.2 数据和网络

- PostgreSQL/Redis 不公网；隧道 ACL 只允许 Gateway 到指定 Jetson 端口；
- 生产 TLS；RK 局域网使用证书 pin/短 token；
- 上传实际探测 MIME/codec，文件名不参与路径；防路径穿越和压缩炸弹；
- Manifest/下载域名 allowlist，防 SSRF；
- NAS mount 使用最小账号，API/Worker 分目录权限；
- 备份和 secret 加密；日志/指标不记录 PII/密钥/签名 URL；
- 依赖/model 有 hash、许可证和漏洞扫描清单。

### 10.3 Secret 管理

- 生产密钥不在 Git、镜像层、Compose 明文、systemd unit、命令行；
- 使用阿里云 Secret Manager/受控 root-owned EnvironmentFile，按环境独立；
- Secret rotation 具备 key ID 和重叠验证窗口；
- 发现泄露立即撤销/轮换并审计，不只从最新 Git 删除；
- `.env.example` 只用 `<generate-random-secret>` 等无效占位符。

## 11. 数据库发布

发布顺序遵循 expand/migrate/contract：

1. 备份和恢复可用性检查；
2. 部署向后兼容 expand migration；
3. `alembic upgrade head`，记录 revision/耗时；
4. 部署 API/Worker，运行 smoke；
5. 后台回填和双读对账；
6. 观察期后独立 release 做 contract/drop；
7. 任何失败按 rollback plan；不能对已不可逆 migration 简单 downgrade 猜测。

上线前在生产快照脱敏副本测试 migration 锁时和磁盘增长。

## 12. 发布和回滚

### 12.1 发布

1. CI：lint/type/test/OpenAPI/Schema/migration/secret scan；
2. 构建不可变 artifact，生成 SBOM/model manifest；
3. Jetson 预拉 release/依赖/模型，验证 hash；
4. 数据库备份，执行兼容 migration；
5. 停止 dispatcher/Worker 领取新任务，等待安全点或依赖租约恢复；
6. 切换 `current` symlink，restart 服务；
7. 健康/smoke/上传小 fixture/创建任务/asset Range；
8. 恢复 dispatcher/Worker，观察队列和错误；
9. 阿里云 Gateway 仅在路径/TLS变更时独立发布。

### 12.2 回滚

- 应用回滚到前一个 release，前提是 DB expand migration 向后兼容；
- analysis pipeline 旧/新产物并存，Track current run 可原子切回；
- 不覆盖 NAS 资产；
- 破坏性 schema/数据变换需要从备份恢复/前向修复，先演练；
- RK 协议版本通过 capability 协商，服务器至少保留当前和前一个兼容版本窗口。

## 13. 备份和恢复

最低策略（最终 RPO/RTO 由业务确认）：

- PostgreSQL：每日全量 + WAL/PITR；加密，至少一份异机/异域；建议 RPO ≤ 15 分钟、RTO ≤ 4 小时；
- NAS：快照/增量备份；媒体可按 content hash 校验；备份不能只和 NAS 同一故障域；
- 配置/secret：加密备份和恢复权限；
- Redis：可丢可重建，不作为唯一恢复来源；
- RK：本地 SQLite WAL 定期 checkpoint；现场 outbox 未确认前不能清理。

每月至少一次抽样 restore，每季度完整灾难恢复演练，记录恢复到哪一时间点、资产/DB 对账结果和实际 RTO。

## 14. 监控和告警

### 14.1 指标

- Gateway：请求量、状态码、p95、upstream connect/time、限流、TLS 到期；
- API：按 operationId 的 QPS/p95/error、DB pool、auth failure；
- PostgreSQL：连接、慢查询、锁、WAL、磁盘、replication/backup；
- Redis：连接、内存、eviction、queue/stream；
- Worker：队列深度/年龄、stage 时间、失败/重试/lease lost、GPU/CPU/RAM/temp disk；
- NAS：mount、read/write latency、容量/inode、IO error；
- Device：last seen、event outbox lag、sequence gap、sync failure、asset hash failure；
- 产品：上传→preview、上传→分析完成、Manifest→cache_ready 成功率/耗时。

### 14.2 告警分级

- P0：数据库/NAS 不可用、数据损坏、TLS 失效、认证大规模失败、资产签名绕过；
- P1：API/隧道不可用、队列持续积压、Worker 全部离线、事件大量缺口；
- P2：单模型降级、单设备长期离线、磁盘 > 80%、备份延迟；
- P3：性能趋势、非关键外部 metadata 失败。

每个告警必须链接 runbook：确认范围、停止扩散、恢复、数据对账、复盘。

## 15. 运维 Runbook 摘要

### Gateway 503

1. 确认 Gateway live、Jetson health、隧道状态；
2. 只做只读诊断，不把流量切到无业务库实例；
3. 恢复隧道/Jetson，验证登录/GET/Range；
4. 检查失败期间 App/RK 重试和事件 backlog。

### NAS 掉载

1. readiness 失败，停止新上传/分析/asset grant；
2. 不把 mountpoint 本地空目录当 NAS 继续写；用 mount guard/device 验证；
3. 恢复挂载，核对 staging/ready asset；
4. 运行 DB ↔ NAS hash/orphan 对账。

### Worker OOM/队列积压

1. 暂停新 Stem 投递、保持 DB 状态；
2. 查看 GPU/RAM、最近 pipeline/model；
3. 恢复 worker，租约接管；
4. 若降并发/回滚模型，记录 release/Run 影响，不手改 completed。

### 数据库恢复

1. 冻结写入/队列；
2. 按选择的时间点恢复到隔离实例；
3. 运行 schema、行数、事件连续性、资产引用检查；
4. 切换并逐步启 API/dispatcher/Worker；
5. 对 RK outbox 重传做幂等确认。
