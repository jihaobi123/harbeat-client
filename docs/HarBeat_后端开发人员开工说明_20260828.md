## 1. 开工前先读这一页

HarBeat 是面向街舞练习、Cypher、Party 和现场活动的智能 DJ 系统，不是单纯的手机播放器。系统的核心分工是：

> 手机提交意图，Cloud/Jetson 生产计划和资源，RK3588 在现场执行并作为播放事实来源。

后端开发实际涉及两类运行环境：

1. **Cloud/Jetson 后端**：FastAPI、PostgreSQL、Redis、音频分析、分轨、排歌、选点、转场渲染和 Manifest。
2. **RK3588 边缘后端**：资源同步、缓存、Operation 编排、音频准备、定时执行、声卡输出和实体按键。

当前仓库同时存在两层代码：

| 层 | 目录 | 含义 |
|---|---|---|
| 当前运行/联调代码 | `app/`、`mobile/`、`web/`、`cypher-integration/rk3588-edge/` | 现有产品和设备实际使用或曾部署的代码 |
| 独立模块代码 | `modules/` | 从运行代码中抽取的合同、clean core 和独立测试；尚未全面替换运行代码 |

因此，开发人员不能看到 `modules/` 中已有实现就直接删除 `app/` 或 `cypher-integration/` 中的旧代码。正确做法是通过 adapter、双读或影子运行完成验证，再逐步切换。

## 3. 整体架构

### 3.1 逻辑拓扑

```text
                                  ┌───────────────────────────────┐
                                  │ Cloud/Jetson                  │
Flutter App ── HTTPS ────────────▶│ Nginx → FastAPI :8000        │
React Web ── same-origin /api ───▶│ PostgreSQL：业务事实          │
                                  │ Redis：缓存/未来任务队列       │
                                  │ NAS/磁盘：歌曲、Stem、Render   │
                                  │ 分析/选歌/选点/Render/Manifest │
                                  └──────────────┬────────────────┘
                                                 │ RK 回源下载资源
                                                 ▼
Flutter App ── LAN HTTP/WS ──────▶ RK3588 edge-agent :9000/:9001
                                      │
                                      ├─ localhost :9100 → sync-worker
                                      ├─ Unix Socket → audio-engine
                                      │                    │
                                      │                    └─ 声卡/音箱
                                      └─ input-daemon ← USB HID 九键/旋钮
```

这里的 **Cloud API 是逻辑边界，不是当前仓库中的另一套独立微服务代码**。目前认证、曲库、推荐、分析、规划和资源接口主要由同一个 FastAPI 模块化单体承载，可部署在 Jetson 后通过公网网关/Nginx 暴露。将来如果把账号或推荐迁到独立云服务，必须通过版本化合同迁移，不能先在文档里假设它已经分离。

### 3.2 各端职责

| 端/进程 | 负责 | 不负责 |
|---|---|---|
| 手机 App | UI、用户意图、preview/confirm、连接、状态展示和任务恢复 | 音频分析、转场渲染、下载编排、判定播放成功 |
| React Web | 曲库、分析和管理界面；调用 Cloud/Jetson API | RK 现场低延迟控制真相 |

| Jetson 分析/渲染能力 | BPM/Beat/Downbeat/Phrase、能量、风格、Stem、排歌、选点、Render | RK 本地播放和现场重新决策 |
| RK edge-agent | 手机入口、Operation、幂等、持久化、同步/准备/调度编排、状态回报 | 复杂选歌、重新分析、重新评分候选 |

### 3.3 权威数据源

| 数据 | 权威端 | 规则 |
|---|---|---|
| 用户、曲库、歌单、分析结果 | PostgreSQL/Cloud-Jetson | 手机缓存不替代业务数据库 |
| Transition Plan、Manifest、算法版本 | Cloud/Jetson | RK 接受后按不可变版本执行 |
| 歌曲、Stem、Render 文件 | Jetson NAS/磁盘或未来对象存储 | 通过 URL、size、SHA256 和 version 发布 |

| Redis | 非权威 | 只用于缓存、锁或任务投递，不替代 PostgreSQL |

## 4. 核心业务链路

### 4.1 歌曲进入曲库

```text
上传/导入歌曲
→ Cloud/Jetson 写入曲库记录和原始文件
→ 离线分析 BPM、Beat、Downbeat、Phrase、能量、风格等
→ 可选 Demucs 四轨分离及 Stem 特征分析
→ 生成版本化分析结果和候选切点
→ 资源通过 Manifest 对手机/RK 可见
```

当前代码仍可能通过请求线程、BackgroundTasks 或启动线程执行重任务。目标正式路径是独立 Worker；在 Worker、业务任务表和可靠重试接入之前，不要继续增加新的进程内长任务。

### 4.2 自动排歌和自动接歌

```text
Jetson 读取已分析歌曲
→ sequence-planner 生成顺序和能量曲线
→ transition-planner 生成相邻 pair 的计划
→ transition-renderer 预生成 WAV/meta
→ Jetson 发布 pair manifest
→ RK 提前同步和准备
→ RK 按本地播放时钟执行并上报事实
```

### 4.3 快切、能量切歌和风格切歌

三种功能只在“目标歌曲如何得到”上不同，用户确认后必须走同一条链路：

```text
手机读取一次 RK playback snapshot/cursor
→ 手机向 Jetson 请求目标预览或 verified plan
→ Jetson 返回确定的 target_song_id、plan 和 pair manifest
→ 手机向 RK 提交一个 Operation
→ RK：sync → cache_ready → prepare → schedule → execute
→ 手机按 operation_id 查询/订阅状态
```

目标状态机：

```text
created → accepted → syncing → cache_ready → prepared → scheduled → executed
                    └──────────────→ rejected | failed | canceled
```

规则：

- HTTP timeout 不等于 `failed`。
- 手机不确定 RK 是否已接收时显示 `status_unknown`，继续查询原 `operation_id`。
- 同一个 `operation_id` 重复提交必须返回原任务，不能重复下载、Render 或 Schedule。
- `executed` 只能来自 RK 的真实播放回执。
- 已确认能量/风格目标后，不得重新随机选歌。
- 失败时当前歌曲继续播放，不能清空队列或造成静音。

### 4.4 当前实现与目标链路的差距

当前运行代码尚未完整实现上述统一 Operation：

- RK 仍有 `/transition/plan` 并导入本地 planner，会在缺少数据时使用默认 BPM、能量和时长继续规划；目标架构应移除这种现场猜测。
- Flutter 仍包含 `SyncWorkerClient`，可直接访问 RK `:9100` 并拼接同步、准备和调度；目标链路只允许手机调用 edge-agent。
- 新的持久化 `operation_id` 状态机尚未全面替代 `/load_plan`、`/xfade` 和兼容接口。
- 老文档中出现过的 orchestrate 路径是目标草案，正式实现前必须先冻结 OpenAPI 和主键语义。

开发新切歌能力时，不要再向旧页面或 RK planner 增加分支；优先完成合同、Operation 和 adapter。

Compose 会用 `.env` 中的 `POSTGRES_*` 变量构造容器内部 `DATABASE_URL`，并等待 PostgreSQL、Redis 健康后启动 app。原生本地运行仍使用 `.env` 的 `localhost` 地址；容器里的 `127.0.0.1` 指向容器自身，不能用来连接宿主机数据库。

## 7. 配置说明

所有真实 Secret 只通过部署环境、受控 Secret Manager 或受限配置文件提供。文档、Git、日志、截图和测试 Fixture 不得包含真实数据库密码、JWT、设备 Token 或完整签名 URL。

### 7.1 Cloud/Jetson 必填配置

| 变量 | 用途 | 开发规则 |
|---|---|---|
| `APP_ENV` | `development`、`test`、`production` 环境识别 | 生产配置必须触发严格安全校验 |
| `APP_HOST`、`APP_PORT` | FastAPI 监听地址和端口 | 容器内通常为 `0.0.0.0:8000` |
| `DATABASE_URL` | PostgreSQL SQLAlchemy URL | 必须由环境注入，不保留生产默认值 |
| `REDIS_URL` | Redis URL | Redis 不是业务事实来源 |
| `JWT_SECRET` | JWT 签名 | 生产缺失时应拒绝启动；需要轮换策略 |

本地临时开关：

| 变量 | 含义 | 规则 |

当前需要特别注意：

- edge-agent 源码中仍有历史默认 Jetson/Gateway 地址，部署必须显式覆盖。
- sync-worker 的 systemd 单元目前监听 `0.0.0.0:9100`，而目标架构要求它只供 RK 本机使用。完成修复前至少使用防火墙阻断 LAN 访问；正式修复应绑定 `127.0.0.1`。
- `EDGE_TOKEN` 为空时部分控制接口为可选鉴权，配对接口也尚未提供正式持久化/过期校验。生产必须修复。
- Unix Socket 权限应收紧为专用用户组 `0660`，不能开放为所有用户可写。

### 7.4 手机地址配置

| 配置 | 当前位置 | 目标 |
|---|---|---|
| Cloud API | `HARBEAT_BASE_URL` dart-define + App 设置 | 应用环境配置的 HTTPS 公网入口 |
| RK API | SharedPreferences + App 设置 | 配对/发现得到的当前 LAN 地址 `:9000` |
| RK WebSocket | edge-agent `:9001/ws` 或兼容 WS | 由 RK endpoint 派生并可重连 |
| sync-worker | 当前旧代码会派生 `:9100` | 新链路中手机不再直接访问 |

不要把 Jetson Tailscale 地址作为普通用户手机的永久默认地址，也不要把某次热点 IP 写死为长期配置。

## 8. 开发方式和代码规则

### 8.1 选择正确的改动位置

| 需求 | 首选改动位置 |
|---|---|
| 登录、曲库、歌单、推荐、Manifest API | `app/modules/<domain>/` |
| BPM、风格、能量、结构和 Stem 特征 | `app/modules/library/` + 对应 clean module/contract |
| 排歌和选点 | Jetson `app/modules/dj_control/` + `modules/sequence-planner`/`transition-planner` |
| Render WAV/meta | Jetson renderer，不放到 RK |
| 资源下载校验 | RK sync-worker/`asset-sync` |
| Operation 状态和幂等 | RK edge-agent adapter + `transition-orchestrator` |
| 真实播放和 DSP | RK audio-engine/`audio-runtime` |
| 手机页面和意图 | `mobile/` + `mobile-dj-control` adapter |
| 实体键和旋钮 | RK input-daemon/`physical-input` |

### 8.2 Cloud/Jetson 模块规范

- Router 只做鉴权、参数校验和响应映射。
- Service 负责业务规则和事务边界。
- Repository/Query 层集中数据库访问。
- 算法函数不直接持有 FastAPI Request 或 SQLAlchemy Session。
- 耗时任务不在 API 请求进程执行。
- API Schema 与内部算法数据结构分开。
- 分析结果、计划、Manifest 和 Render 都携带 schema/algorithm/renderer version。

### 8.3 跨端合同变更

每次 Jetson、RK 或手机共享接口变更必须同时提交：

1. OpenAPI 或 JSON Schema。
2. 向后兼容和回滚说明。
3. Jetson 合同测试。
4. RK/Flutter 消费端 Fixture 测试。
5. 数据库变更对应的 migration。
6. 错误码、日志字段和可观察性说明。

合同的目标单一事实来源建议为：

```text
contracts/openapi/jetson.yaml
contracts/openapi/rk.yaml
contracts/schemas/manifest/
contracts/schemas/operation/
docs/adr/
```

这些目录目前尚未完整成为生产合同源。建立后，禁止各端根据聊天记录或旧页面自行猜字段。

### 8.4 Git 和提交规则

- 从团队确认的 onboarding/integration ref 创建短生命周期分支。
- 一个 PR 聚焦一个模块边界或一个可独立回滚的目标。
- 不提交歌曲、Stem、Render WAV、模型权重、数据库、生产 cache、APK、Token 或设备备份。
- 不直接修改 Jetson `/opt/harbeat/current` 或 RK `/home/cat/cypher` 作为唯一代码来源。
- 接入 clean module 时保留旧实现和回滚开关，先跑行为对比。
- 未通过真实三端验证前，不把模块标记为 production integrated。

## 9. Docker、部署和发布

### 9.1 当前 Docker 能做什么

当前 `Dockerfile`：

- Node 20 构建 React Web。
- Python 3.12 运行 FastAPI。
- 安装 CPU 版 PyTorch/torchaudio。
- 将 `web/dist` 放进 API 镜像。

当前 `docker-compose.yml`：

- 启动 `app`、`postgres`、`redis`、`nginx`。
- PostgreSQL 和 Redis 带健康检查，app 等待两者 ready。
- 不启动 RQ Worker。
- Nginx 只配置 HTTP `:80`，没有完成 TLS。

所以它适合作为当前开发/CPU 基线，不能直接代表 Jetson GPU 生产部署。`deploy/JETSON_SETUP.md` 中描述了 Jetson GPU 方向，但其中提到的 `Dockerfile.jetson`、`requirements-jetson.txt` 等文件当前并未完整落入仓库，执行前必须按实际代码重新核对。

### 9.2 Jetson 发布要求

推荐流程：

1. 从干净 clone 和明确 SHA 构建不可变 release/镜像。
2. 验证 Secret、数据库、Redis、存储、模型和 NAS 挂载。
3. 备份数据库并执行版本化 migration。
4. 启动 API 和 Worker，运行 live/readiness。
5. 切换 Nginx 或 `/opt/harbeat/current` 软链接。
6. 运行登录、曲库、分析任务、Manifest、资源下载和 RK 联调冒烟。
7. 保留上一版本和数据库兼容说明。

### 9.3 RK 发布要求

- 使用版本目录或可审计部署包，不用 SCP 覆盖零散文件作为最终发布。
- 先验证 cache 和配置目录，再替换代码。
- 按 systemd 依赖顺序重启。
- 验证 `:9000`、`:9100`、Unix Socket、声卡、九键和断网行为。
- 失败时回滚整个版本，不手工拼接旧新文件。

## 15. 最终原则

HarBeat 下一阶段不需要先拆大量微服务。当前最重要的是：

1. 冻结一个所有人都能获得的代码基线。
2. 用版本化合同固定 Jetson、RK 和手机之间的边界。
3. 把重任务移出 API，把播放执行留在 RK。
4. 用持久化 Operation 保证幂等、恢复和现场事实一致。
5. 通过 adapter 将 13 个 clean module 逐步接回运行代码。
6. 用真实手机、Jetson、RK、声卡和实体按键完成端到端验收。

在这六项完成前，任何单机测试、Mock 或文档声明都不能单独证明系统已经具备生产交付状态。
