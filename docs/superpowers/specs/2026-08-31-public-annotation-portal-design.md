# HarBeat 公共标注入口设计

## 背景

Jetson 当前公网根页面是原有 HarBeat 网站。这个网站后续还要继续承载曲库、播放和其他 API，不能被标注页面替换。

远端分支 `origin/codex/bar-understanding-v1` 已经有一套按小节标注段落及人声、鼓、贝斯、旋律状态的工作台，但它沿用私人曲库的权限模型：用户只能看到自己上传的歌，标注文件也只有每首歌一份。直接部署会导致新注册用户看不到 Pilot 歌曲，多人保存时还可能覆盖彼此结果。

本次改动在保留原网站的前提下新增公共标注入口。任何人可以注册账号，查看同一批 Pilot 歌曲，并独立保存自己的标注。

## 目标

- `/` 继续显示原网站，现有页面和 API 行为不变。
- 新增 `/annotate`，未登录时允许注册或登录，登录后直接进入标注工作台。
- 原网站侧边栏增加“公共标注工作台”入口。
- 所有注册用户看到相同的 10 首 Pilot 歌曲。
- 每位标注者拥有独立的 Revision 历史，不能读取、修改或覆盖其他人的草稿。
- 支持汇总导出“歌曲 × 标注者”的 JSONL，供后续比较和裁决。
- 在 Jetson 生产环境部署并完成双用户隔离验证。

## 不在本轮处理的内容

- 不删除或重做原网站。
- 不开放整座私人曲库，也不允许公共标注者上传、删除或修改歌曲。
- 不在本轮计算标注者一致性、自动投票或最终真值。
- 不改变已生成的 Presence 候选文件和数据集版本。
- 不处理当前可用歌曲中缺少长 Intro、稀疏鼓点样本的问题。

## 页面与入口

前端保留现有单页应用。它根据浏览器路径选择入口：

- `/`：现有 HarBeat 网站。
- `/annotate`：公共标注工作台。

访问 `/annotate` 时如果没有有效登录状态，显示现有注册/登录表单。登录完成后仍停留在 `/annotate`，不跳回旧首页。已经登录的用户直接进入工作台。

标注工作台以远端 `bar-understanding-v1` 的 `AnnotationWorkbench` 为基础，保留连续小节选择、系统建议、段落标签、四种音乐元素状态、循环试听和 Revision 提示。歌曲下拉框改为读取公共 Pilot 清单，不再读取当前用户的私人曲库。

原网站侧边栏增加入口，但原有导航、曲库和播放器不做删减。

## 后端边界

现有 `app.modules.annotations` 已用于 Presence 标注，不能被远端分支中同名模块覆盖。新的 Bar Understanding 功能放入独立模块 `app.modules.bar_annotations`，路由统一使用 `/api/bar-annotations`。

需要提供以下接口：

- `GET /api/bar-annotations/pilot/tracks`：返回允许公共标注的歌曲清单。
- `GET /api/bar-annotations/tracks/{track_id}/workspace`：读取公共机器候选和当前用户自己的最新修订。
- `PUT /api/bar-annotations/tracks/{track_id}/workspace`：只保存当前用户的标注。
- `GET /api/bar-annotations/tracks/{track_id}/audio`：只读播放白名单歌曲的原音频。
- `GET /api/bar-annotations/tracks/{track_id}/stems/{stem_name}`：只读播放白名单歌曲的四轨 Stem。

这些接口全部要求有效登录令牌。它们不复用私人曲库的“歌曲必须属于当前用户”判断，而是检查歌曲是否在 Pilot 白名单中。其他曲库和流媒体接口继续使用原来的所有权规则。

## Pilot 白名单

第一轮白名单使用已经生成 Presence 候选的 10 首歌曲。生产环境从配置文件读取 ID，启动时验证：

- ID 对应的歌曲存在；
- 原音频路径可读；
- 至少有可用的 Beat Grid 或 downbeat；
- 四轨 Stem 路径存在时才显示 Stem 播放按钮。

白名单文件和应用代码分开保存。以后增减歌曲不需要改页面代码，但每次更新仍要经过启动校验。

## 标注数据隔离

机器候选是公共只读数据。人工标注按用户分开保存，目录结构为：

```text
/data/harbeat/bar-annotations/
  bar-understanding-1.0.0/
    users/
      <user_id>/
        <track_id>.json
```

每份文件包含数据集版本、歌曲 ID、标注者 ID、时间轴指纹、Revision、更新时间和标注记录。保存时服务端从登录令牌取得用户 ID，不接受前端传入的标注者身份。

Revision 只在“用户 × 歌曲”范围内递增。两个用户可以同时标同一首歌，不会触发冲突；同一用户打开两个页面并同时保存时，后保存的页面收到 409，需要重新加载。

标注文件采用文件锁、临时文件和原子替换。时间轴发生变化时拒绝继续写入当前数据集版本，避免旧小节索引被静默套到新时间轴。

## 注册与权限

继续使用现有用户名、密码和 JWT 登录机制。公共注册不要求管理员邀请，但需要以下限制：

- 注册和登录接口做基础的按 IP 频率限制；
- 用户名保持唯一；
- 密码沿用后端现有的强度和哈希规则；
- 公共账户不能通过 Bar Annotation 接口上传或删除歌曲；
- Pilot 音频接口只接受白名单歌曲和固定的四种 Stem 名称。

本轮不新增管理员页面。清单更新和汇总导出由服务器脚本完成。

## 汇总导出

新增命令行脚本，遍历指定数据集下的所有用户目录，输出：

- JSONL：每条记录保留 `track_id`、`annotator_id`、任务、Bar 范围、值、状态和创建时间；
- 报告 JSON：用户数、歌曲数、每位用户的完成度、每首歌的标注人数、未完成项和解析失败文件。

脚本只读取人工标注，不修改线上数据。无法通过结构验证的文件进入报告错误列表，不写入 JSONL。

## 错误处理

- 未登录或令牌过期：返回 401，页面保留 `/annotate` 地址并显示登录表单。
- 歌曲不在 Pilot 白名单：返回 404，不泄露私人曲库是否存在该 ID。
- 时间轴不可用：返回 422，并在页面提示先修复歌曲分析。
- Revision 冲突：返回 409，页面允许放弃本地草稿后重新加载。
- 音频或 Stem 文件缺失：返回 404；其他标签仍可继续审核，但页面明确显示对应音源不可用。
- 同时保存：文件锁保护单个“用户 × 歌曲”文件，不阻塞其他标注者。

## 测试与验收

实现按测试驱动方式进行。自动化测试至少覆盖：

1. 新用户可以注册并访问 `/annotate`。
2. 两名用户读取到相同的 10 首 Pilot 歌曲。
3. 两名用户在同一首歌保存不同标注后，各自读取到自己的版本。
4. 用户不能通过请求参数伪造其他标注者身份。
5. 同一用户用旧 Revision 保存时得到 409。
6. 非白名单歌曲和非法 Stem 名称不能通过公共接口读取。
7. `/`、私人曲库、现有流媒体和 Presence API 的回归测试通过。
8. 汇总脚本能同时导出两名用户的记录，并保留各自身份。

部署到 Jetson 后再做一次浏览器验收：保留旧首页；分别注册两个临时账号；打开 `/annotate`；播放同一首歌；保存不同标签；刷新后确认两边结果没有串线。验收账号和测试标注随后清理，不进入正式 Pilot 汇总。

## 发布与回滚

发布采用新的只读代码目录和独立持久化数据目录。先在 Jetson 的临时端口验证，再切换生产服务。Nginx 需要把 `/annotate` 回退到同一份前端 `index.html`，API 转发规则保持不变。

回滚时恢复上一个应用发布目录即可。`/data/harbeat/bar-annotations` 不随代码回滚删除，避免已经保存的标注丢失。重新上线后继续读取同一数据集目录。

## 完成条件

以下条件全部满足后，本轮才算完成：

- 原网站根页面和现有 API 正常；
- `/annotate` 可以注册、登录、查看 10 首 Pilot 并播放音频；
- 不同用户的标注文件和 Revision 相互独立；
- 汇总脚本可以列出所有标注者；
- Jetson 重启后页面、API 和已保存标注仍然存在；
- 自动化测试和生产浏览器验收均通过。
