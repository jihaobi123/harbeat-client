# V3 在线混音决策日志

每次用户点击“下一首”“提高／降低能量”“切换风格”或指定歌曲，以及曲目将结束时自动发起的混音，都生成独立 `requestId`。同一请求等待当前交接完成后继续处理时沿用原编号。`planId` 标识实际排入音频时钟的计划。

页面的“逐次混音决策日志”按触发时间显示记录，包括没有找到方案、加载失败、被新请求替代、取消和超时。最近一次成功安排的计划另外显示，失败请求不会被误当成这个旧计划。

## 查看与导出

- **导出全部日志**：JSON，格式 `harbeat.v3_live_session.v2`，保留完整事件、原始数值、规则版本、预处理来源、候选排序及音频线程记录。
- **导出决策说明**：Markdown，逐次说明选点和混音方案的理由，附完整候选和事件链，方便同事阅读。
- 页面每批展示 20 次触发，可以展开更早记录。候选表展示前 10 名，导出保留全部合格候选。
- 日志保留在当前页面会话内，取消和停止不会清除，超过 1500 条也不会删除旧记录。**刷新或关闭前需要导出；本次没有增加浏览器持久存储或服务器收集接口。**

## 一次触发记录什么

| 内容 | 依据 |
| --- | --- |
| 用户意图 | 触发来源、当前歌曲和原曲位置、指定歌曲／风格／能量方向、初始预算与截止时点 |
| A 切出点 | 原曲秒数、原始小节网格索引、相邻段落边界、边界距离、等待时间 |
| A 开始混入点 | 按交接终点减去进入素材时长反推；最近原始首拍及误差；65 ms 门槛 |
| B 切入点 | 进入窗口的原曲起止位置、2／4 小节长度、对应网格及段落；交接后正文起点 |
| 变速 | A BPM、B 原速 BPM、素材变速比、交接长度、名义原曲／播放时间映射；交接后恢复原速 |
| 人声 | 两侧原始重叠区间、扩展 0.3 秒后并集占比和时长、5% 与 0.5 秒门槛是否满足 |
| 排名 | 等待、变速幅度、人声风险、段落边界、四小节、同风格的原始值、权重及分数贡献；第二名差值及同分处理方式 |
| 排除 | 指定歌曲／风格不符、素材缺失或未解码、能量方向、正文长度、变速范围、错过进歌点、预算、曲尾及网格误差；按曲目／窗口／原因统计次数 |
| 模板 | 固定 V3 线性淡化、双轨增益、EQ 参数和恢复时间；是否触发 B 中频衰减 |
| 来源 | 曲目、报告及运行标识、原音频／素材 SHA256、输入附带的来源信息和待确认警告 |
| 结果 | 安排、锁定、取消、被替代、停止、失败、超时或完成；以及关联计划的音频处理块观察 |

网格索引是原始分析数组的零起始位置，不是已人工确认的小节编号。边界接近只表示规则加分；不会把未经确认的 intro／verse／chorus 变成确定事实。

## “选择方案”到底表示什么

当前搜索的是歌曲、进入窗口和交接时间，所有合格候选按原有 V3 Live 规则排序。新增日志没有改变权重、门槛或 EQ／淡化参数。

**混音模板固定为 `v3_linear_eq`，没有比较其他混音算法。** 日志因此明确记录 `alternativesEvaluated: []`，不会声称这个模板在多算法比较中获胜。低频和高频参数沿用 V3，不是根据本次频谱遮蔽自适应求出的；人声条件只决定 B 中频是否衰减。调性、和弦、乐器与审美分没有参与这套模板选择。

规则分不代表音质概率。两个窗口都检测到人声，也不等于它们每一时刻都同时唱歌。能量曲线仍未完成跨曲感知校准。

## 事件顺序与失败定位

```text
request_received
  ├─ request_outcome: rejected
  ├─ request_deferred → request_resumed（原 requestId）
  │                    或 request_outcome: expired / superseded / stopped
  └─ decision_search: ready_assets
       ├─ decision_search: preparation_preview
       │    → preparation_started → preparation_completed
       │    → decision_search: after_preparation
       └─ plan_scheduled → plan_locked
            → audio_observation / handoff_state_commit
            → request_outcome: completed
```

任一准备阶段可以失败、取消、被新请求替代或停止，这些请求同样保留结果。准备前选中的窗口只是暂定候选，下载后必须使用剩余预算重新搜索；日志分开保存两个阶段，避免把过期的暂定点误认为已执行点。

`plan_scheduled` 中的开始、EQ 恢复和完成时间采用同一个 AudioContext 时钟。`audio_observation` 记录音频处理块经过目标帧的时刻，带原 `requestId` 和 `planId`。`handoff_state_commit` 是控制状态接管记录，不能当作实际出声证据。扬声器、声卡和蓝牙延迟仍未测量。

## 实现与验证

- `web/src/realtime/decision.ts`：从实际选中计划生成解释、数值依据和来源。
- `planner.ts`：保留原筛选及排序，增加每项筛除原因和计数。
- `transport.ts`：请求关联、分阶段候选快照、唯一最终结果及完整会话导出。
- `DecisionHistory.tsx`：逐次记录与 Markdown 导出；音频播放进度刷新时不重复渲染整份历史。

104 项前端测试通过。使用真实六首歌在不同播放位置、预算、意图和素材准备状态下对比旧版，共 1080 组，候选顺序、得分、进出点、变速比和人声处理开关完全一致。原 V3 和 381 个预处理源码文件校验保持不变。
